# 代码评审与技术债治理方案

## 目标与适用范围

本方案面向题栈（AlgoStack）多轮需求调整、迁移和修复后的代码现状。目标不是把代码统一成某种写法，而是找出会反复造成缺陷、增加变更成本或阻碍验证的根因，并以可验证的小批次消除。

方案编写时参考 `main` 的 `b22a4f6226c655244cb00a9c766babed4f0629dc`，工作区干净。已核对近期提交、工程结构、构建任务和部分关键调用链；**这是一份执行方案，不是全仓评审结论，也不是已确认的债务清单**。正式执行时重新固定目标 SHA、工作区范围及环境；并行修改不自动混入。

本轮计划评审当前实现，不限于最近一次 diff。历史提交只用于解释决策、定位引入点和判断是否已修复，不逐个重审全部历史。范围包括 Kotlin 业务与 IDEA 集成、WebView、资源与注册、桥接脚本、测试和分发文档。

沿用 [AGENTS.md](../AGENTS.md) 和[工程结构](工程结构.md)的边界：仅支持 LeetCodeCN，固定 Java／Go 新题约定，不恢复数据库、旧 XML 状态、自定义用例或其他平台。明确接受的限制不登记为缺陷；确有改变需求时，先单独确认，而不是借技术债治理扩展功能。

## 一、总体方法：沿调用链查证，再跨模块归纳

每条主链都按同一个顺序检查：

> 用户输入／平台事件 → 参数与身份 → 状态变化 → 网络或文件副作用 → UI／Console 交付 → 取消与释放

先回答“什么场景下会发生什么”，再讨论是否需要调整职责和抽象。不能只看某个方法正确，就认为整条链路正确；也不能因为方法长、有重复或存在 `catch`，直接判为债务。

近期修复提供了三个值得复用的评审切入点，但不应重新计为未解决问题：

- `825eebc`、`f9d102c` 的查询修复说明：后台不再发布旧结果，不等于 UI 不会应用旧结果；状态相等性还会影响结果能否再次交付。
- 提交受理信息的修复说明：HTTP 已成功、事件已发出、Console 已输出，是不同的完成阶段；每次挂起都需要检查取消边界。
- 编辑器上下文、Java 骨架、重名另存和 WebView 运行时的迭代说明：局部逻辑、平台装配、最终产物和真实客户端分别需要证据。

正式 CR 既检查这些保护是否仍成立，也检查相邻入口是否存在同类遗漏，不机械复制修复措施。

## 二、八个评审角度

以下路径中的业务包均位于 `src/main/kotlin/io/github/yungyu16/algostack/`。表内内容是检查问题，不代表已经存在缺陷。

| 角度 | 重点核查 | 项目入口与所需证据 |
|---|---|---|
| 1. 需求与历史兼容 | 删除的功能是否还残留入口、模型或配置读取；固定约定是否被个别调用方绕过；旧项目是否被意外改写 | `activities`、`configuration`、`plugin.xml`、模板与初始化入口；需求文档、注册关系及旧文件字节不变的回归 |
| 2. 行为与协议契约 | 题目身份、提交区域、后台 questionId、语言映射是否一致；成功、空结果、错误和取消是否可区分；Accepted 与判题状态是否混淆 | `domain`、`execution`、`leetcode/api`；沿真实入口追踪参数，核对序列化、GraphQL 资源及消费者，不只看 DTO |
| 3. 并发、线程与生命周期 | 状态由谁拥有；EDT、read/write action 和后台 I/O 是否分工正确；状态发布与 UI 应用是否分别保护；视图／项目关闭后任务及资源是否收尾 | `LatestQuery`、`ArticlesPanel`、`SidebarContext`、`AuthenticationSession`、浏览器与桥接；时序图、受控调度回归和实际释放证据 |
| 4. 安全与副作用 | 新文件是否覆盖旧文件；路径及软链接边界是否符合已声明策略；提交超时是否盲目重试；凭据、桥接 token、远端内容和本地资源是否隔离 | `FileOperations`、`GeneratedChallengeFile`、`ChallengeInitialization`、`ChallengeBridgeServer`、`CookieStore`、`WebResources`、`LeetCodeFrameHandler`；失败注入、权限与协议校验，不访问真实凭据或历史库 |
| 5. 模型、职责与可读性 | 入口能否看清业务步骤；状态和副作用是否藏在构造或回调中；协议对象是否承担 UI／生命周期职责；同一规则是否有多个来源；抽象是否有实际策略或复用价值 | `ExecutionService`、`ChallengesView`、`ArticlesPanel`、初始化与浏览器代码；列出一次真实需求需要改哪些位置、为什么容易漏，不能仅凭行数提出拆分 |
| 6. 异常、性能与诊断 | 是否吞掉必要错误或取消；缓存是否有失效与容量边界；轮询能否退出；EDT 是否执行阻塞操作；失败后能否定位到阶段且不泄露敏感内容 | HTTP、认证、头像／标签缓存、Console、iframe 流式代理；异常传播路径、日志样例及必要的耗时／资源数据，不凭猜测引入缓存或复杂重试 |
| 7. 测试有效性 | 测试是否经过生产逻辑及真实消费者；是否只检查方法返回值、漏掉装配与排队窗口；测试能否在旧实现失败；是否依赖时间碰运气或个人环境 | `src/test`、`scripts/test_initialize_challenge.mjs`、`webview/plugin/runtime.test.mjs`；断言对象、替身边界、超时与清理逻辑，而不是只看测试数量 |
| 8. 依赖、产物与维护文档 | 插件 ID、动作注册、DumbAware、资源动态加载及暗色变体是否完整；源码/JAR/ZIP/已安装版本是否对应；依赖和废弃 API 是否影响目标平台 | `build.gradle.kts`、`gradle.properties`、`plugin.xml`、`webview`、README 与 docs；锁定依赖、最终包、Verifier 和客户端验收分别给出结论 |

### 结构债务的判定标准

以下信号值得调查，但必须说明具体成本才进入治理：

- 同一业务规则在多个入口复制，已有修复只覆盖其中一个入口。
- 一个对象同时管理无关生命周期，导致无法单独关闭或验证其中一部分。
- 模型字段命名或含义跨层变化，调用方依赖隐含约定才能正确使用。
- 关键流程只能启动完整 IDEA、登录真实站点才能验证，且这种耦合妨碍经常变更的纯逻辑回归。
- 需求已经删除，但保留的兼容分支仍参与运行、增加歧义或维护成本。

反例：Java/Go 生成与身份识别使用不同解析方式有不同目的；保护状态发布和保护 EDT 应用不是重复逻辑；为释放资源捕获异常不等于吞错；仅因命名仍带历史标识，不能修改已有配置和凭据契约。先核实语义再决定是否收敛。

## 三、按风险安排评审批次

### 批次 A：数据与执行安全

优先看两条链：

1. 手动打开／Agent 初始化 → 模板渲染 → 冲突处理／最终文件名 → 新文件写入 → 工程初始化 → 编辑器打开。
2. 编辑器动作 → 当前内容识别 → 保存与再次核验 → 平台题目数据 → 测试／提交 → 受理 → 轮询 → Console。

必须覆盖：已有文件、未保存 Document、重名另存、非法输入、部分成功、取消、网络失败、平台已受理但跟踪失败。重点核对普通请求的重试与非幂等提交是否分开。

**本批出口：** 有证据的文件安全、身份错误或重复提交风险均被说明；成立问题具备最小复现及处理建议。没有运行证据的部分标为待验证，不说“全部安全”。

### 批次 B：状态与 IDEA 生命周期

检查启动／登录恢复、查询／切题、编辑器动作上下文、WebView／预览打开与关闭、本机桥接的项目绑定。每类可变状态注明所有者、修改线程、失效条件和释放者，不要求为所有字段绘图。

优先时序：旧请求排队、新请求替换；相同结果连续返回；登录或退出发生在请求中；项目关闭发生在网络或 EDT 排队中；索引期间调用编辑器或预览入口。

**本批出口：** 关键交接点有可解释的取消、锁与释放语义；确定性测试和真实 IDEA 验收缺口分别列出。

### 批次 C：结构收敛与残留清理

基于前两批反复出现的根因，再判断是否需要抽取职责、统一状态模型、收敛参数来源或删除废弃代码。优先处理“一次修复要改多处且已经漏改”的位置，不先制定全仓新架构。

资源删除须检查代码、`plugin.xml`、动态消息键、GraphQL 回退、平台隐式加载及产物引用。`rg` 无命中只作为候选，不能单独证明可删除。废弃 API 按目标平台的实际兼容影响排序，不以消除全部 warning 为目标。

**本批出口：** 每项结构调整都能说明减少了哪种实际成本；可删内容有无消费者证据；其余保持原状或记录延期条件。

### 批次 D：验证与交付闭环

核对测试是否覆盖前几批的风险，而不是只覆盖新抽出的辅助函数。检查最终 JAR、插件 ZIP、发布说明、目标 IDEA 和安装记录之间的对应关系；把尚未完成的客户端验收整理成短清单。

**本批出口：** 每项治理能关联问题、提交和验证；不会把单测、打包成功或旧版安装记录外推为当前版本已可用。

这四批是顺序与决策点，不是四个大提交。A/B 的紧急缺陷可独立处理；C/D 不应成为推迟高风险修复的理由。

## 四、执行流程与协作

### 1. 固定范围，建立基线

- 记录分支、目标 SHA、staged／unstaged／untracked 和 upstream；本轮现状审计与后续增量评审分别标注。没有 fetch 就不宣称远端已核对。
- 核对项目指令、当前功能边界、依赖与平台版本、测试入口和历史验证证据。
- 输出主链覆盖表：已读入口与调用方、已核对的保护、尚未覆盖的场景。不得用“全仓看过”代替覆盖说明。

### 2. 只读 CR，形成候选清单

沿批次检查，不边阅读边顺手重构。独立模块可交给 reviewer，但使用相同目标版本，并明确原始需求、路径、关注点和只读边界；协调者复核调用链、已有保护与反例，合并同一根因。

搜索工具用于定位候选；本地源码、锁定版本和实际消费者优先。只有平台 API 契约不清、涉及易变行为或本地证据不足时查询对应版本官方资料。

### 3. 复现与分诊

只读阶段不运行构建或测试。进入验证阶段后，在用户授权的本地执行范围内增加或运行定向回归；真实登录、提交、安装、卸载及外部操作另行确认。使用替身、临时文件和可丢弃项目，不读写用户历史数据。

对疑点依次排除：上游校验、框架锁或生命周期保护、明确接受的限制、后续已修复的实现。可以确定的纯逻辑问题不强求真实站点复现；运行态风险没有证据就保留为风险。

### 4. 确认治理范围，再分批实现

先提交评审结论与建议顺序；只有获准的治理项进入实现。一个独立根因一个变更单元，必要时先补特征测试，再做结构调整；行为修复与无关改名、搬包、格式化分开。

每批结束后由另一视角复核：修复是否覆盖完整消费者、是否扩大取消保护、是否改变协议或引入新状态源。复核不以同一作者的说明代替源码证据。

## 五、债务清单与优先级

### 不把所有发现都叫技术债

| 类型 | 判定 | 处理 |
|---|---|---|
| 已确认缺陷 | 有可达场景和明确错误行为 | 按影响修复；若由共性结构导致，再登记根因债务 |
| 维护债务 | 当前可工作，但有证据表明增加变更成本、重复出错或阻碍验证 | 比较局部修补与结构调整的收益、风险和验证成本 |
| 待验证风险 | 有疑点但尚未证实保护缺失或实际影响 | 明确下一项验证及所需环境，不按故障发布 |
| 可选改进／接受的限制 | 偏好差异、低收益清理，或有意保留的行为 | 不阻塞交付；记录理由或不进入清单 |

优先级与证据确定程度分别记录，不用主观总分掩盖未知项：

- **P0：立即处置。** 已证实的严重数据破坏、凭据泄露等不可接受风险；是否存在须经查证，不预设本项目有此类问题。
- **P1：下一批优先。** 常见核心链路不可用，或可达的误提交、覆盖文件、持续资源泄漏等高影响问题。
- **P2：计划治理。** 有条件触发的正确性问题、反复漏改的重复规则、关键测试缺口或显著维护负担。
- **P3：按需处理。** 局部可读性、非关键诊断、低影响文档或清理问题；不与高风险问题一起扩大重构。

同级项按触发频率、影响范围、近期是否会再次修改、修复风险和验证成本排序。没有可靠工时依据时只写工作量等级及未知项，不承诺未经估算的日期。

### 每项记录模板

正式发现集中记录在一份项目内清单，建议为 `docs/技术债清单.md`，有首条有效发现时再创建，不额外建立平行 TODO 系统。

| 字段 | 内容 |
|---|---|
| 标识／标题 | 稳定编号及具体问题，不写“代码需要优化” |
| 类型／优先级／状态 | 缺陷、债务、风险或可选项；候选、已确认、待治理、验证中、已关闭、接受或延期 |
| 适用版本与位置 | 目标 SHA、路径及行号；注明本轮新增、历史遗留或既有修复未闭环 |
| 场景与证据 | 触发条件、真实调用链、源码／测试／运行证据；已有保护和反例 |
| 影响与不处理成本 | 用户后果或具体维护成本；不以文件长、重复率高代替解释 |
| 治理选项 | 最小修复、必要的结构调整及不处理的取舍；兼容边界和预计工作量 |
| 验收与恢复 | 可失败的回归、人工验证、产物检查；代码回退是否足够，有无不可逆外部副作用 |
| 责任与追踪 | 负责人、修复提交、验证证据；延期原因和重新评估条件 |

没有必要为一次性疑点创建永久条目。已关闭项保留根因及证据链接即可，不持续堆积过程日志。

## 六、验证与治理完成标准

| 层次 | 要证明的事 | 不能替代的事 |
|---|---|---|
| 纯逻辑／协议回归 | 身份、区域、生成、参数、错误语义正确；必要时证明旧实现失败 | IDEA 装配、真实平台响应 |
| 确定性时序回归 | 用闸门、受控调度等覆盖替换、取消和释放窗口；有超时与清理 | 完整项目关闭、插件卸载或真实窗口交互 |
| 平台集成与产物 | 注册／动作上下文、JAR 资源、依赖与 ZIP 对应；目标平台 API 可用 | 安装成功及运行效果 |
| 客户端验收 | 在明确版本与可丢弃项目中验证真实交互和资源释放 | 未经授权的真实提交或对全部平台行为的保证 |

每个治理批次按风险执行定向验证，再执行工程标准检查；环境准备、定向命令和人工验收见[开发指南](开发指南.md)：

```bash
./gradlew check buildPlugin verifyPluginProjectConfiguration
```

改动平台 API、扩展注册或目标版本时，安排 Plugin Verifier；未执行或受环境阻塞必须记录。最终包与安装结果单独检查，不因构建通过宣称已安装。

一项治理关闭须同时满足：

1. 问题与治理范围明确，关键行为及兼容约束未被意外改变。
2. 修复经过对应验证，证据绑定实际源码与产物；未覆盖部分明确，不把“未复现”写为“已修复”。
3. 同根因的关联入口已检查；不要求无证据地全仓推广新抽象。
4. 文档与测试反映当前契约；已完成与待执行的验收分开。
5. 有独立可追踪提交及恢复说明。遵守项目版本和 CHANGELOG 规则；纯文档不机械升版，不混入并行修改，不擅自推送或发布。

对需要真实环境才能关闭的项，代码完成后仍标为“验证中”，不靠测试数量清零债务。

## 七、建议首轮交付

首轮建议先完成 **批次 A/B 的只读评审与候选分诊**，不要立即做全仓结构调整。交付内容控制为：

1. 一张主链覆盖表，标出数据写入、请求提交、UI 交付和资源释放的边界。
2. 一份去重后的发现清单，分开明确问题、维护债务和待验证风险。
3. 下一批建议处理的少量高收益项目，说明最小改动、验证方式及不处理的影响；没有成立问题就不凑数。
4. 一份短验证缺口清单，明确哪些需要 IDEA、Verifier、受控网络或用户授权。

治理是否有效，主要看同类回归是否减少、关键失败路径是否可验证、一次需求是否不再需要遗漏风险很高的多处同步修改，而不是删除多少行、拆出多少类或增加多少测试。没有这些收益证据的“整洁化”不优先。
